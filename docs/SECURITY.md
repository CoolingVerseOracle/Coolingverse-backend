# 백엔드 보안 적용 내역

CoolingVerse 백엔드에 적용된 보안 조치와 그 이유, 그리고 의도적으로 단순화한 부분을 정리한 문서입니다.
(B2G 관리자 1인 전용 서비스라는 전제에 맞춘 설계입니다. 2026-07-28 기준)

## 1. 비밀번호 보호

| 조치 | 내용 |
| --- | --- |
| BCrypt 해시 저장 | 비밀번호 원문은 어디에도 저장하지 않음. 환경변수에도 BCrypt 해시만 보관 |
| 환경변수 주입 | 관리자 계정(`ADMIN_ID`, `ADMIN_PASSWORD_HASH`)은 OCI 환경변수로 주입. DB에 계정 테이블 없음 |
| 코드에 비밀 없음 | 저장소에는 로컬 테스트용 해시 기본값만 존재 (원문 아님). 운영 배포 시 환경변수가 덮어씀 |

## 2. 인증 (정적 토큰 방식)

| 조치 | 내용 |
| --- | --- |
| 예측 불가능한 토큰 | 서버 기동 시 SecureRandom 32바이트로 생성 (무차별 대입으로 추측 불가) |
| 서버 재시작 = 전원 로그아웃 | 토큰이 메모리에만 존재하므로 재시작하면 기존 토큰 전부 무효 (세션 방식과 동일한 성질) |
| Bearer 헤더 전달 | 토큰은 쿠키가 아닌 `Authorization` 헤더로만 주고받음 |

## 3. 접근 통제

| 조치 | 내용 |
| --- | --- |
| 전면 인증 필수 | `/login` 하나만 공개, 나머지 모든 API는 토큰 없으면 **401** (B2G 특성상 조회조차 비공개) |
| 무상태(stateless) | 서버 세션을 만들지 않음 → 세션 하이재킹·고정 공격 표면 자체가 없음 |
| 계정 열거 방지 | 로그인 실패 시 아이디가 틀렸는지 비밀번호가 틀렸는지 구분해서 알려주지 않음 (동일 메시지) |

## 4. 웹 공격 방어

| 조치 | 내용 |
| --- | --- |
| CORS 화이트리스트 | 허용 출처를 `http://localhost:5173`(프론트 개발서버)로 제한. 메서드·헤더도 필요한 것만 허용. 배포 시 실제 프론트 주소만 추가 |
| CSRF 비활성화 (의도적) | CSRF는 브라우저가 쿠키를 자동 전송하는 것을 악용하는 공격인데, 본 서비스는 쿠키를 아예 쓰지 않으므로(토큰 헤더 방식) 공격이 성립하지 않음 → 표준 관행에 따라 비활성화 |
| 입력 방어 | 로그인 필드 누락, 시나리오 필수값 누락 등 비정상 입력에 500 대신 안내 응답 (내부 정보 노출 방지) |

## 5. DB 접속 보안 (Oracle 연결 준비분)

| 조치 | 내용 |
| --- | --- |
| 접속정보 환경변수화 | ADB 사용자/비밀번호/Wallet 경로는 전부 환경변수(`ADB_USERNAME` 등)로 주입. 코드·저장소에 하드코딩 금지 |
| Wallet 방식 | Oracle ADB는 Wallet(인증서 묶음) 기반 암호화 접속만 허용 — 전송 구간 암호화 기본 적용 |

## 6. 의도적으로 단순화한 것 (한계와 근거)

관리자 1명 · 내부 시연용이라는 전제로, 아래는 적용하지 않았습니다. 서비스가 커지면 재검토 대상입니다.

- **토큰 만료 시간 없음** — 서버 재시작 시 무효화로 갈음. (다중 사용자 서비스라면 만료+갱신 필요)
- **로그인 시도 횟수 제한 없음** — 관리자 1계정뿐이라 위험 낮음. (공개 서비스라면 필수)
- **HTTPS는 배포 단계 과제** — 로컬 개발은 HTTP. OCI 배포 시 HTTPS 적용 필요
- **권한 등급 없음** — 관리자 단일 역할(ROLE_ADMIN)만 존재. 소유권 검사 불필요(1인 확정)

## 검증 상태

- 로그인 성공/실패/필드 누락, 무토큰 401, CORS preflight — 전부 자동 테스트 및 실호출로 검증 완료
- 브라우저 동일 조건(출처 5173) 시뮬레이션으로 실제 연동 경로 검증 완료
